## 1. Login Page

**What the user sees:** A form with phone number, PIN, and a link to register.

### Login flow
**What happens:** User types phone + PIN, clicks Login.

1. [LoginController.java#L23](src/main/java/com/igirepay/lab3_mini_capstone/controller/LoginController.java#L23) — `handleLogin()` validates the fields (phone can't be empty, PIN must be exactly 5 digits via `isValidPin()` at line 96)
2. It calls `service.isAccountLocked(phone)` — if the account is locked, login is blocked immediately
3. [`JdbcWalletService.java#L148`](src/main/java/com/igirepay/lab2_jdbc/service/JdbcWalletService.java#L148) — `loginByPhone()` calls `CustomerDAO.findByPhoneAndPin()` which runs:
   ```sql
   SELECT * FROM customers WHERE phone_number = ? AND pin = ?
   ```
4. If credentials are wrong, [`CustomerDAO.java#L152`](src/main/java/com/igirepay/lab2_jdbc/dao/CustomerDAO.java#L152) — `incrementFailedAttempts()` adds 1 to the `failed_attempts` column. After 3 failures, `lockAccount()` sets `is_locked = TRUE`
5. On success → `SessionManager.getInstance().setCurrentCustomer(customer)` stores the logged-in user in memory (Singleton pattern)
6. Role is fetched via `getRoleByPhone()` → if `ADMIN`, goes to `admin` screen; otherwise `dashboard`

**Key design point to explain:** SessionManager ([SessionManager.java](src/main/java/com/igirepay/lab3_mini_capstone/util/SessionManager.java)) is a **Singleton** — there's only ever one instance, so every controller can call `SessionManager.getInstance()` to know who is logged in.

### Registration flow
**What happens:** User fills name, email, phone, PIN, confirm PIN → clicks Register.

1. [LoginController.java#L68](src/main/java/com/igirepay/lab3_mini_capstone/controller/LoginController.java#L68) — `handleRegister()` validates all fields: email format, phone must match `^07\d{8}$`, PIN must be 5 digits, PINs must match
2. Creates a `new Customer(0, name, email, phone)` and calls `service.registerCustomer(customer, pin)`
3. [`CustomerDAO.java#L12`](src/main/java/com/igirepay/lab2_jdbc/dao/CustomerDAO.java#L12) — runs a single INSERT with name, email, phone, pin, and default role `"USER"`. Uses a **transaction** (`setAutoCommit(false)`) — if anything fails, it rolls back so no broken record is left
4. Returns the new customer ID shown to the user as confirmation

## 3. Transactions Screen (Deposit / Withdraw / Transfer)

**What the user sees:** Three tabs — Deposit, Withdraw, Transfer.

**Where it's implemented:** [TransactionController.java](src/main/java/com/igirepay/lab3_mini_capstone/controller/TransactionController.java)

### Deposit / Withdraw
1. User selects their account from a dropdown, enters an amount and PIN, clicks submit
2. `handleSubmit()` (line 128) verifies the PIN first via `service.login(customerId, pin)` — if wrong PIN, transaction is cancelled
3. A unique reference ID is generated: `"TXN-" + UUID.randomUUID()...` — this is how duplicate prevention works
4. `service.processTransaction(customerId, accountId, ref, amount, type)` is called
5. In [JdbcWalletService.java#L65](src/main/java/com/igirepay/lab2_jdbc/service/JdbcWalletService.java#L65) — it first calls `idempotencyService.validateReference(ref)` which checks the `processed_requests` table. If the same ref was used before → throws `DuplicateTransactionException`
6. Then calls `account.processTransaction()` — this is **polymorphism**: the same method call behaves differently depending on whether it's a `WalletAccount` or `SavingsAccount`

### Fee system
[WalletAccount.java#L19](src/main/java/com/igirepay/lab1_oop/model/WalletAccount.java#L19) — `withdraw()` calls `TransactionFee.getWalletFee(amount)` and deducts `amount + fee`.

[SavingsAccount.java#L22](src/main/java/com/igirepay/lab1_oop/model/SavingsAccount.java#L22) — `withdraw()` uses `TransactionFee.getSavingsFee(amount)`. In [TransactionFee.java](src/main/java/com/igirepay/lab1_oop/util/TransactionFee.java) — savings fee is **8% of amount** unless it's the last 5 days of the month (then free).

SavingsAccount also enforces a **minimum balance of 500 RWF** — if going below that, it throws `InsufficientBalanceException`.

### Transfer
1. User enters receiver's phone number → clicks Lookup
2. `handlePhoneLookup()` (line 103) resolves the receiver via `service.findCustomerByPhone()`. It shows a confirmation card with receiver's name
3. User can't transfer to themselves — checked at line 113
4. On submit, `service.transfer(senderCustomerId, senderAccountId, receiverPhone, ref, amount)` is called
5. [JdbcWalletService.java#L99](src/main/java/com/igirepay/lab2_jdbc/service/JdbcWalletService.java#L99) — transfer saves **two transaction records**: one `TRANSFER_OUT` on sender's account and one `TRANSFER_IN` on receiver's account

## Key OOP Concepts to Highlight in Interview

| Concept | Where |
|---|---|
| **Inheritance** | `WalletAccount` and `SavingsAccount` both extend abstract `Account` |
| **Polymorphism** | `account.processTransaction()` behaves differently per account type |
| **Encapsulation** | All fields in model classes are private with getters/setters |
| **Singleton** | `SessionManager` — one instance shared across all controllers |
| **DAO Pattern** | `CustomerDAO`, `AccountDAO`, `TransactionDAO` — each handles one table |
| **Duplicate Prevention** | `IdempotencyService` checks `processed_requests` table before every transaction |
| **PreparedStatement** | All SQL in DAOs uses `?` placeholders — prevents SQL injection |
| **Transactions (DB)** | `CustomerDAO.save()` uses `setAutoCommit(false)` + rollback for safe registration |
